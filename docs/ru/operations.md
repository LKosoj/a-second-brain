# Эксплуатация

[English](../en/operations.md) | [Оглавление документации](../index.md)

Запускайте A Second Brain от отдельной непривилегированной учётной записи
Linux. Штатная установка использует systemd user units и не создаёт сервис от
имени root. Команды на этой странице предполагают исходный checkout и рабочий
systemd user manager. В экземпляре, созданном только из wheel, штатного
установщика units нет.

## Проверка в foreground

Перед включением сервисов:

```bash
cd /path/to/a-second-brain
uv run --frozen --no-dev a-second-brain doctor --smoke
uv run --frozen --no-dev a-second-brain run
```

Убедитесь, что `/menu` работает из Telegram-аккаунта владельца, затем
остановите foreground-процесс.

## Установка systemd user units

Создайте units, не включая их:

```bash
./scripts/install-systemd-user.sh
```

Проверьте файлы в `~/.config/systemd/user/`. После проверки включите штатные
units:

```bash
./scripts/install-systemd-user.sh --enable
```

Перед включением установщик запускает `doctor`.

## Поставляемые units

| Unit | Назначение |
|---|---|
| `a-second-brain.service` | Telegram-бот |
| `a-second-brain-process.timer` | Ежедневная обработка в 21:00 по умолчанию (`DAILY_PROCESS_TIME`) |
| `a-second-brain-morning-brief.timer` | Утренний бриф в 08:00 по умолчанию (`MORNING_BRIEF_TIME`) |
| `a-second-brain-plaud-sync.timer` | Ежечасная синхронизация PLAUD, если она настроена |
| `a-second-brain-qmd-maintenance.timer` | Еженедельная очистка QMD при наличии `qmd` |
| `a-second-brain-backup-verify.timer` | Еженедельная проверка бэкапа, воскресенье 04:15 |

Чтобы сменить время, задайте `DAILY_PROCESS_TIME` / `MORNING_BRIEF_TIME`
(`HH:MM`) в `.env` и заново запустите `scripts/install-systemd-user.sh`;
неверное значение он отклонит. Если задан `TIMEZONE`, оба таймера получают
пояс (`OnCalendar=*-*-* 21:00:00 Europe/Moscow`), и время считается по часам
владельца при любом поясе сервера; после смены `TIMEZONE` запустите установщик
заново. Перед классификацией ночной запуск также
повторяет распознавание голосовых записей с пометкой «Не распознано» за вчера и
сегодня.

Перед ежедневной обработкой с записью запускается предварительное
зашифрованное резервное копирование. Если GPG-получатель не задан, этот этап
сообщает о пропуске и успешно завершается.

## Команды Telegram

| Команда | Действие |
|---|---|
| `/do` | Выполнить произвольный запрос (текстом, голосом, аудиофайлом, кружком, фото или документом) |
| `/why` | Объяснить, почему собранная страница так говорит |
| `/find` | Искать заметки по словам, без модели |
| `/undo` | Удалить последнюю запись за сегодня |
| `/reminders` | Показать ожидающие напоминания |
| `/process`, `/process_full` | Предпросмотр или запуск дневной обработки |
| `/menu` | Открыть панель |
| `/stats` | Статистика записей (`/status` - старый псевдоним) |
| `/files` | Просмотр файлов vault |
| `/help` | Показать список команд (`/start` показывает тот же текст) |

`/find <запрос>` запускает `qmd search` (поиск по словам, без модели) и
показывает до пяти результатов с путём и фрагментом; кнопки «📄 N» присылают
файл. Без запроса бот ждёт текст 10 минут; `-` или повторный `/find` отменяет
поиск, а команды (`/...`) сбрасывают ожидание и выполняются как обычно. `qmd` должен быть в `PATH`, иначе бот ответит, что поиск недоступен.
Запрос не попадает в сессию и дневную заметку. Скрытые каталоги (например,
`.session`) и `skills/` не выдаются. Ограничения: поиск идёт по словам (без
морфологии и смысла), зависит от индекса qmd (свежая заметка может пока не
найтись). qmd нормализует имена файлов в адресах (`Заметка Проба #1.md`
возвращается как `Заметка-Проба-1.md`); бот восстанавливает имя тем же
правилом, что и qmd. Если одно нормализованное имя подходит двум файлам одной
коллекции, результат не показывается, чтобы не выдать не ту заметку.

`/undo` показывает последнюю запись за сегодня и просит подтверждения. Удаляется
только запись в дневной заметке (не вложения и не собранные страницы), только за
текущий день владельца (`TIMEZONE`, см. [Конфигурация](configuration.md)) и не
запись, которую ночной запуск уже обработал.

Правка обычного текстового сообщения или подписи к фото в Telegram обновляет
сохранённую запись. Если ночной проход уже обработал запись или у фото не было
подписи, исправление добавляется в дневную заметку отдельной записью. Если
правка пришла раньше, чем бот записал сообщение в сессию, бот ждёт эту запись
до 5 секунд; если она не появилась, а сообщение уже есть в дневной заметке,
исправление тоже добавляется отдельной записью. Команды («/...») записями не
считаются, а запись, удалённую через `/undo`, правка не возвращает.

Фото или документ, отправленные в режиме `/do`, сохраняются как обычно (вложение
и запись в дневной заметке), а подпись выполняется как поручение по этому файлу.
Без подписи бот просто разбирает файл. Подпись пересланного сообщения поручением
не считается. Альбом сохраняется одной записью, и поручение выполняется один раз
по всем его фото.

`/reminders` показывает ожидающие напоминания. Создать напоминание можно
фразой вроде «напомни завтра в 9 позвонить».

## Управление сервисом

```bash
systemctl --user status a-second-brain.service
systemctl --user restart a-second-brain.service
systemctl --user stop a-second-brain.service
systemctl --user start a-second-brain.service
```

Юнит бота использует `KillMode=mixed`: при остановке или перезапуске бот
сначала получает SIGTERM и закрывает свои сессии tmux, затем systemd убивает
всё, что осталось в юните. Работающий юнит сохраняет старый `KillMode`, пока
вы не запустите `scripts/install-systemd-user.sh` (он переустановит шаблон) и
`systemctl --user daemon-reload`. Учтите, что `mixed` при остановке или
перезапуске завершает и дочерние процессы бота, поэтому запущенный в этот
момент вызов CLI прерывается. Если бот умер, не закрыв сессии (сбой, SIGKILL),
следующий запуск бота удалит оставшиеся серверы tmux с мёртвым владельцем;
сессии живого процесса, например ночного запуска, остаются нетронутыми.

Проверка таймеров:

```bash
systemctl --user list-timers 'a-second-brain-*'
systemctl --user status a-second-brain-process.timer
```

## Логи

Приложение пишет в stdout и stderr. При запуске через systemd используйте
journal:

```bash
journalctl --user -u a-second-brain.service -n 200 --no-pager
journalctl --user -u a-second-brain.service -f
journalctl --user -u a-second-brain-process.service --since today
```

Перед публикацией логов проверьте, нет ли в них записанного текста, путей,
Telegram ID и ошибок провайдеров с чувствительными данными.

## Обновление исходного checkout

Перед значительным обновлением остановите процессы, которые могут писать
данные:

```bash
for unit in \
  a-second-brain-process.timer \
  a-second-brain-morning-brief.timer \
  a-second-brain-plaud-sync.timer \
  a-second-brain-qmd-maintenance.timer \
  a-second-brain.service \
  a-second-brain-process.service \
  a-second-brain-morning-brief.service \
  a-second-brain-plaud-sync.service \
  a-second-brain-qmd-maintenance.service
do
  systemctl --user stop "$unit" 2>/dev/null || true
done
git pull --ff-only
uv sync --frozen --no-dev
uv run --frozen --no-dev a-second-brain doctor
./scripts/install-systemd-user.sh --enable
```

Если изменились deployment-шаблоны, установщик выполнит `daemon-reload`.
Перед миграциями изучите release notes и создайте проверенную резервную копию.

## Ручной запуск обслуживания

```bash
uv run --frozen --no-dev python -m d_brain.run_daily_process --mode scheduled
uv run --frozen --no-dev python -m d_brain.run_plaud_sync
uv run --frozen --no-dev a-second-brain qmd cleanup
uv run --frozen --no-dev python -m d_brain.run_vault_backup
```

Ручные команды используют тот же `.env` и рабочий каталог, что и сервисы.

Чтобы откатить записи одного прогона в vault, используйте
`a-second-brain recover <run_id>`; чтобы вручную подрезать журнал операций,
`a-second-brain ops-prune` (см. `docs/ru/cli.md`). Перед обеими командами
остановите бота и убедитесь, что ночная обработка не идёт.

## Работа после выхода из системы

Обычно пользовательские сервисы останавливаются, когда у учётной записи нет
активной сессии. Администратор может включить lingering для выделенной учётной
записи:

```bash
sudo loginctl enable-linger <service-account>
```

Это решение уровня хоста, поэтому установщик проекта намеренно его не
принимает автоматически.
